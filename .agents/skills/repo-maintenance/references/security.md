# Security alert workflow

1. Inventory the requested scope using available GitHub security alerts and ecosystem audits, including production and development dependencies. Record counts, advisory IDs, affected package versions, dependency paths and severity; distinguish GitHub alert state from package-manager audit results. Re-run against the final lockfile because advisory data and dependencies change.
2. Evaluate each advisory against actual use: what ships in the extension or webview, what only runs in build, docs, install or release, the untrusted input and vulnerable code path, and whether that path is reachable. Use advisory details and installed source where necessary. State uncertainty; a package in a lockfile does not alone establish exploitation, and an absent function does not prove the whole package safe. Do not expose exploitable details or secrets in public discussions where private reporting is needed.
3. Prefer compatible patched versions or removal/replacement of unused or unmaintained dependencies. Review new dependencies, provenance, transitive changes, install scripts and credentials. Treat cross-major overrides, native installers, release tooling and out-of-range peers as compatibility risks requiring explicit validation. Avoid blanket upgrades, suppressions or force-merges that conceal unresolved issues.
4. Exercise behavior at relevant trust boundaries with focused tests; run appropriate unit, build, webview, VS Code E2E, docs, packaging and CI checks. For a native installer or release path, distinguish local fixture tests from actual remote downloads or publication. Create and merge a tested PR when authorized. Document each advisory's disposition and actual impact, any remaining scanner findings or unresolved risk, evidence and test limits; recheck alerts after merge. Do not claim alerts are cleared merely because a PR was merged.
