# Pull request workflow

1. Inspect the PR description, discussion, base and head SHA, full diff, commit history, checks and linked issues. Identify conflicts, stale assumptions and changes outside the stated purpose. For forks, inspect the diff and dependency/lifecycle changes before checking out or executing code; use an isolated environment and avoid exposing credentials to untrusted code.
2. Review behavior, data loss, privilege boundaries, input handling and tests. Examine every added or upgraded dependency and its provenance, version, transitive and install-time behavior, licenses where material, and known advisories. Assess the actual reachable impact; do not equate a clean scanner with proof of safety. Watch CI, workflow, shell and release-script changes especially closely.
3. Run targeted tests and relevant builds, packaging and CI. Resolve genuine failures or coordinate a safe fix on an authorized branch. Re-review if the PR head or base changes. Do not merge a PR with unresolved correctness or security concerns, failed required checks, or missing evidence for a high-risk change.
4. Merge a suitable PR after checks and required reviews pass, using the exact reviewed head SHA. Close an unsuitable, superseded or unfixable PR with a specific, accurate explanation; if more information is essential, request it and explain how the author can reopen or resubmit. Do not discard valid work solely to make the queue empty; explain material blockers when a safe decision is not possible. Verify merge/close state and linked issues afterward.
